# Autonomous Monitoring Evidence Refresh

## Purpose

Sentinel Level 2 monitoring must decide from one current evidence window. A
previous recovery classification, ratio, or endpoint ranking must never replace
facts derived from the newest monitor snapshot.

This layer is read-only with respect to production. It may update local reports,
state, playbooks, and audit records. It cannot enable LOW_LIVE, execute a remote
write, search for credentials, or change website infrastructure.

## Required Order

Every canonical production pipeline run follows this order:

1. Identify the newest local monitor snapshot.
2. Refresh the local website observation if it references another snapshot.
3. Refresh fixed first-party route evidence using read-only probes.
4. Rebuild Phase 10.22 recovery from the selected snapshot.
5. Compare all four snapshot identities.
6. Build Canonical Truth only when the identities are equal.
7. Render Daily, Master, and Pipeline output from that canonical result.
8. Validate the rendered outputs against the canonical fields.

The four identities are:

```text
latest_monitor_snapshot
website_report_snapshot
origin_matrix_snapshot
recovery_baseline_snapshot
```

An absent or unequal identity produces `EVIDENCE_WINDOW_MISMATCH`. Website,
route, and recovery sources are then excluded from current operational truth.
No legacy value is substituted.

## Recovery Supersession

The current NowPlaying classification and dominant 504 share are owned by the
Phase 10.22 recovery module. Older route-mismatch diagnostics remain explicitly
legacy and informational. The dominant share is recalculated from current
canonical counts when the dominant endpoint is NowPlaying.

Phase 10.22 recovery is rebuilt before canonical resolution even when the
snapshot ID has not changed. This prevents results generated by an older
algorithm from surviving a code deployment merely because they share the same
input snapshot.

## Autonomous Decisions

The monitoring decision vocabulary is intentionally small:

```text
NO_ACTION
MONITOR_CONTINUE
OWNER_ACTION_REQUIRED
```

All three decisions execute as `NO_ACTION`. They choose the next read-only
diagnostic or owner escalation; they are never productive apply instructions.
When the exact failure layer is not proven, Sentinel records correlation,
confidence, missing evidence, and an owner-gated next step.

## Safety Invariants

```text
LOW_LIVE=false while the write canary is blocked
MEDIUM=false
HIGH=false
cloudflare_write=false
remote_write=false
credential_search=false
repair requires proven cause, exact scope, and rollback
```

A point-in-time healthy origin probe can narrow a failure boundary but cannot
prove the historical internal failure layer. Without verified first-party
origin access, the next origin-log correlation remains
`REMOTE_OWNER_ACTION_REQUIRED`.
